## Теория (60 мин)
### RAD
- Пример контроллера - какие есть недостатки?

### Table-Driven Development
- Active Record
- ORM - отвязываем от таблицы
- Анемичная модель

### Model Driven Development
- Фокус не на структуре таблиц, а на кодовой модели объектов предметной области, их структуре, правила и поведении

### Блоки: Entity
- Объект, который имеет уникальный идентификатор и жизненный цикл.
- Проверяет свое состояние и обеспечивает целостность данных.
- При создании проверяет инварианты.
- Каждая мутация переводит из одного целостного состояния в другое целостное.
- Проверки и в конструкторе и в мутациях = дублирование проверок  - можно вынести в отдельный объект.

### Блоки: Value Object
- Объект-значение, который не имеет уникального идентификатора и не изменяется.
- Проверяет свое состояние, придавая смысл значениям.
- Два разных объекта с одинаковым значениями считаются равными.

### Вопрос: где Entity и где Value Object на схеме? про куплюру?
- Сущности и объекты значения помогают нам придать смысл примитивным типам и структурам PHP.

### Блоки: Aggregate
- Несколько связанных сущностей, которые меняются вместе в рамках одной транзакции
- Всегда есть главная сущность
- Может состоять из одной сущности

- Агрегат не может иметь объектных ссылок на другие агрегаты, вместо этого - идентификаторы.

- Агрегат - это про тактические границы. Вы сами определяете где они проходят, нет правил. Чем меньше тем лучше
    - Пример с MealPlan -> Days -> Meals -> Recipes -> Ingredients -> Measurement Units
    - Тренировка: выделите на схеме агрегаты
 
- Если несколько агрегатов меняются одновременно, то это может привести к рассинхрону... Придется жить с Eventual Consistency. Не везде применимо, например в банковских транзакциях, но в 90% случаях да.


### Repository
- Нужно упомянуть, что репозиторий мы делаем только для агрегатов!
- Для составных частей не делаем
- Репозиторий реализует интерфейс Collection
- Репозиторий не содержит бизнес логики, не создает объекты, только сохраняет и извлекает агрегаты.

### Event Driven Development
- Агрегаты генерируют события
- События отправляются в шину событий
- Доменные события обрабатываются слушателями в рамках той же транзакции.
- Доменные события могут быть оптравлены в шину сообщений и слушаться другими контекстами

- На самом деле все сложнее, доменные события обрабатываются в рамках той же транзакции внутри домена, а для кросс-контекстной выделяют интеграционные события.

### Event Sourcing
- События хранятся в журнале событий и объекты восстанавливаются из них.

### CQRS
- Команды меняют состояние и ничего не возвращают
- Запросы возвращают результат и ничего не меняют

- Зачем нужен?
    - Разделение ответственности между командами и запросами
    - Оптимизация производительности запросов, в командах - DQL, в запросах чистый SQL
    - Чтения можно масштабировать независимо (например, на реплики).
    - Команды можно оптимизировать за счёт очередей, асинхронных команд и event sourcing.

Добавим новый модуль - Sales, твиттер по подписке.

  - `Create`   -> `SubscriptionCreated`

  - `Create` -> `InvoiceCreated`

- Добавляем модель `Subscription`
- Обращаем ввнимание, что на пользователь и продукт ссылаемся по идентификатору, а не объекту.
- В фабричном методе обращаем внимание на логику: устанавливается в статус PENDING

```php
<?php

declare(strict_types=1);

namespace bravik\Sales\Domain\Model\Subscription;

use bravik\Sales\Domain\Model\Price;
use bravik\Shared\Domain\Model\OId;
use DateTimeImmutable;


class Subscription
{
    public function __construct(
        private OId $id,
        private OId $customerId,
        private OId $productId,
        private Price $price,
        private Status $status,
        private DateTimeImmutable $startDate,
        private ?DateTimeImmutable $endDate = null
    ) {
    }

    public static function create(
        OId $customerId,
        OId $productId,
        Price $price,
        DateTimeImmutable $startDate,
        ?DateTimeImmutable $endDate = null
    ): self {
        $subscription =  new self(
            OId::next(),
            $customerId,
            $productId,
            $price,
            Status::PENDING,
            $startDate,
            $endDate,
        );

        return $subscription;
    }

    public function getId(): OId
    {
        return $this->id;
    }

    public function getCustomerId(): OId
    {
        return $this->customerId;
    }

    public function getProductId(): OId
    {
        return $this->productId;
    }

    public function getPrice(): Price
    {
        return $this->price;
    }

    public function getStartDate(): DateTimeImmutable
    {
        return $this->startDate;
    }

    public function getEndDate(): ?DateTimeImmutable
    {
        return $this->endDate;
    }

    public function isPending(): bool
    {
        return $this->status === Status::PENDING;
    }

    public function isActive(): bool
    {
        return $this->status === Status::ACTIVE;
    }

    public function isCancelled(): bool
    {
        return $this->status === Status::CANCELLED;
    }

    public function isExpired(): bool
    {
        return $this->status === Status::EXPIRED;
    }
}
```

#### Подписка (Subscriptions/Create)
- Пользователь подписывается на продукт
- Создается подписка в статусе `pending`
- Пользователю возвращается идентификатор новой подписки
- По событию `SubsriptionCreated` создается счет на оплату
- Тут `$endDate` по хорошему должен быть где-то внутри домена, а не в команде, так как это бизнес-логика
- Эта команда нарушает принцип того, что команда не возвращает результат

#### Получение ссылки на оплату
- Пользовательский UI по идентификатору подписки поллит бэкэнд для получения ссылки на оплату
- Когда инвойс будет создан, бэкэнд вернет ссылку на оплату

#### Оплата и активация подписки
- Пользователь переходит по ссылке и оплачивает счет
- Платежный счет вызывает HTTP вебхук при успешной оплате. Действие `Invoice.Pay`
- По событию `InvoicePaid` подписка переводится в статус `active`. Действие `Subscription.Activate`

- Фасад использует на входе и на выходе только примитивы, либо DTO объекты со слоя `Presentation`. Все эти DTO - чсть контракта
- Реализацию храним тут же.
- Реализация фасада перенаправляет вызов каждого метода нужному сценарию использования

  - Обращаем внимание, что мы кидаем `Throwable` на все исключения. В контракте нужны свои исключения и в фасаде надо переводить с языка Application в язык контракта.

- Можно не делать все это, а просто использовать сценарии использования напрямую, это уже улучшит организацию кода
